Cron expressions are five fields of terse punctuation, and a wrong guess means a job that silently never runs — or runs a thousand times more often than you meant. Paste one here to read it back in plain English and see exactly when it will next fire.

Cron syntax is compact and unforgiving, and the errors it produces are silent: a job that never runs looks the same as a job that has not run yet. Two mistakes account for most of them. `0 0 * * 0` is weekly, not daily — the fields are minute, hour, day-of-month, month, day-of-week, and it is easy to shift by one. And when both day-of-month and day-of-week are restricted, standard cron runs on either, not on both, so `0 0 13 * 5` fires every Friday as well as every 13th.

This page describes an expression in plain language and lists the next several times it will actually fire, which turns "I think this is right" into something you can check before a job spends a week not running. It reads the standard five-field form — the one crontab, Kubernetes CronJobs and most schedulers use. Quartz and Spring accept a six-field variant with a leading seconds column; drop that column before pasting an expression in here, or every field will be read one position to the left.

list_alt How to use Cron Expression Generator & Parser

  1. Type or paste an expression into the big field, or start from one of the presets below it.
  2. Adjust individual fields with the five dropdowns — each one accepts free text too, so you can type "*/15" or "MON-FRI" directly.
  3. Read the Meaning panel to confirm the schedule matches your intent.
  4. Check "Next 10 runs" — the times are in your own time zone, with the gap to each one shown beside it.
  5. Copy the finished expression with the button in the field.

lightbulb Tips & gotchas

  • The most common cron mistake: setting both day-of-month and day-of-week. Cron treats them as OR, not AND, so "0 0 13 * 5" fires on the 13th AND on every Friday. The Meaning panel spells this out when it applies.
  • Servers usually run in UTC while you read times locally. The next-run list uses your browser time zone — compare it against your server before trusting a deployment.
  • "Matched values" expands each field into the exact list of numbers it allows, which is the quickest way to spot an off-by-one in a range.
  • Named shorthands like @daily and @hourly are accepted and expanded for you.

help_outline Frequently asked questions

Does this support 6-field (seconds) or Quartz expressions?

The parser expects the standard 5-field crontab format used by Linux cron, Kubernetes CronJobs and most CI systems. Quartz "?" is accepted as a synonym for "*", but Quartz-only extensions such as L, W and # are not supported.

Why does my expression say it never runs?

The combination is impossible — most often a date that does not exist, such as "0 0 30 2 *" for the 30th of February. Widen the day or month field and the run list reappears.

Is 0 or 7 Sunday?

Both. Cron accepts 0 and 7 for Sunday, and this tool normalises 7 to 0 internally, so either form produces the same schedule.
